supragnosis v0.11.0

Upgrade, reconnect Claude Code, restart; a session starts with what its project recorded.

Changes since v0.10.3.

Upgrade the server and the app, run supragnosis connect claude-code once, then restart; a session starts with what its project recorded, and the remote surfaces are gone. brew upgrade, then supragnosis connect claude-code if you use Claude Code, then supragnosis restart. The store format and the sync protocol are unchanged, so a 0.10 node and a 0.11 node still sync. Two MCP changes are breaking for an agent that relied on the old behaviour; they open the next section.

Read before upgrading

  • A write names its workspace. observe, define_type and propose refuse a call without workspace, and every tool refuses an argument it does not know, naming it. A write that left the workspace out used to land in the node's default, and on a real node one project's entities had piled up there. Reads go the other way: list_proposals, workspace_map and the brief and curate prompts read every workspace when none is named, as search_knowledge already did.
  • Server profiles, principals and consent to serve are removed (remote-server.md Section 13). No one used a server elsewhere, and about 3,000 lines of code had to be stepped around by every change. Gone: supragnosis server and supragnosis principal, client.toml, the SUPRAGNOSIS_SERVER_URL, _TOKEN_FILE and _CA variables, the hub's /mcp and /viz/, [sync] serve_workspaces, join --serve, and the app's Server pane. If you made a server profile, delete ~/.supragnosis/client.toml and the credentials under ~/.supragnosis/servers/: nothing reads them now. [[server.principals]] and serve_workspaces still parse and do nothing; the daemon's log and sync_status say they can be removed. server --json goes with its command; status --json keeps its server field as {"name": "local", "remote": false}.
  • Run supragnosis connect claude-code once. The hook now answers a third event, a subagent's start, and an install connected before this reads as capture off until connect adds the missing group. The two groups it had keep working meanwhile.
  • A bare supragnosis typed in a terminal prints its help. Run with no arguments it used to open the store as a stdio server, and a person who typed it held the store's lock. Through a pipe, the way an MCP client launches it, it still serves; supragnosis serve starts it from anywhere.

A session starts with what its project recorded

A two-week look at the author's own Claude Code sessions found the store written to far more than it was read: 252 records made, 44 reads, about two reads that changed what the agent did next (recall.md Section 1). What reached an agent without asking was used; what had to be searched for mostly was not.

  • The index. At a session's start, after a compaction too, the hook gives the agent its workspace's newest 25 records: the day, the first sentence, and the link that opens the record, fenced as evidence and not instructions. A subagent gets the newest 10. Then two lines on how to search the rest: two or three English topic words, the project's workspace, and the resource that opens an observation.
  • The question after a commit now says what is worth recording that the diff does not show: a choice the person made, an option ruled out, a number measured, a constraint. After a compaction the agent is asked to record what its summary holds that the records do not.
  • Use is recorded as provenance. When a record shaped a new one, the agent is asked to name it in derived_from, which observe already took. A link copied there is kept as the record's id.
  • Two defects found on the way. A workspace whose records name no entity is listed, and get_entity given an observation's id says how to open it.

Four days in, on the same machine and with every caveat a sample that small carries (recall.md Section 7.2): reads went from about five a day to about twelve, and from 0.07 to 0.32 per hundred tool calls, partly because there were fewer tool calls; writes grew faster still, so reads per write did not rise. Most records opened were lines of the index. In a busy project the newest 25 reach back only hours, which is the next thing to study.

What the agents use, kept on the machine

  • A usage log. The daemon appends a line to ~/.supragnosis/usage.jsonl for every MCP call it answers - the function, the workspace named, the app, what it came to - and the hook adds a line for each index it gives and each commit it asks about. No query, record text, entity name or record id is written; a commit id is, so a commit question can be joined to the record that answers it. The file is the owner's alone (0600), is not in the store, and is never synced or sent.
  • supragnosis usage reads it: calls by function and workspace, by app, and what the hook gave, over --since 7d or any number of days or hours; --json gives the same as data.
  • Settings > Usage in the app shows the same over 7, 30 or 90 days, with the trends by day: calls split by function, workspace, app or read and write; what found nothing or failed; the indexes given and the commit questions answered; records opened from an index; writes that cite a record. Every chart has its numbers in a table.

Sync

Three corrections from a review of the sync code (sync-correctness.md Section 16):

  • The credential is checked before the body. A sync request without an admitted credential is refused with 401 before its body is read.
  • A sequence number cannot wrap. A reservation past the largest number fails the round with the workspace named, and nothing is stamped.
  • A rejection nobody can clear is dropped. An event that is malformed, or names the wrong workspace, is reported and passed over, so the stream behind it carries on. An event whose signature does not verify still holds its stream.

Smaller changes

  • A reproject writes its projection in one transaction, not one a row. On a copy of the author's store, 458 rows took about 0.3 s instead of about 2.6 s. A hub reprojects after every accepted push, and a spoke after every pull.
  • What "human confirmed" proves is said as it is. A confirmation is made in the app on one of your machines, by you or by a program running as you, and the viewer now says so instead of "a person confirmed it". The server instructions and the review and propose descriptions tell agents the tier is the person's own act, never to be cast by a tool. The server instructions also tell every MCP client, not only Claude Code, to search before settling a question the project may already have settled.
  • Dependencies. pulldown-cmark 0.13.5 for RUSTSEC-2026-0414, in the end-to-end report renderer only, which never set the affected option.

Under the hood

The four largest source files - the engine's lib.rs, the CLI's and the app's main.rs, and the viewer's script - are split into modules, and the tests that searched source text for a phrase now call the code or request the page. Nothing a user meets changes with either.
