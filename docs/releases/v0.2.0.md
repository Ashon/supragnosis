Changes since v0.1.21.

**Cozo is gone.** `redb` is the store - the only file-backed one - and the C++ RocksDB bridge that
came with Cozo is gone with it. Building supragnosis no longer needs `clang` or `libclang-dev`, on any
platform, and both CI workflows dropped the step that installed them.

This is a breaking change for an existing node, and the one thing to read before upgrading.

## Upgrading from a Cozo store

**v0.1.21 is the last release that can read one.** This build refuses to start when it finds an
un-migrated Cozo store rather than coming up empty beside it, so the migration cannot be skipped by
accident - only postponed.

```bash
supragnosis stop
curl -fsSL https://supragnosis.dev/install.sh | sh -s -- --version v0.1.21
supragnosis migrate-store            # copies the log, then replays it
curl -fsSL https://supragnosis.dev/install.sh | sh   # back to latest
supragnosis start
```

Only the observation log is copied; the entity/relation graph is a projection of it and is rebuilt by
replay. The Cozo store is opened read-only and left untouched.

**Read [`docs/store-migration.md`](../store-migration.md) Section 5 first.** A replay reproduces
exactly what the log asserts and nothing else, which is correct and can look like data loss: rows
written into the projection outside the log - early-era direct writes, test fixtures - do not come
across. In the author's own store that was 72 entity rows out of 440. On a node whose knowledge
arrived through observe and federation it was zero. Check yours before switching; if any of it is
knowledge you want, re-assert it through `observe` first, which is where it should have been.

`migrate-store` is not in this release. The command belongs to the release that can still read the
format it migrates from, and doing otherwise would mean carrying the whole Cozo adapter forward to
serve a one-time act.

## Highlights

### What the Datalog was actually buying

Measured, not assumed. The adapter ran nineteen query shapes, of which exactly one was genuinely
recursive - `traverse`'s bounded BFS. The rest were point get/put on four relations, scans with a
workspace filter, a two-rule union for `relations_of`, and an ANN lookup. No time-travel operator
appeared anywhere. And the `query` passthrough has never been opened (Principles 12/21), so Datalog
was an implementation detail of one adapter rather than a surface anything else depended on.

Against that: Cozo's last release was 2023-12-11, and `cozorocks` was the only reason the build
needed a C++ toolchain. Replacing a query engine with a B-tree plus two secondary indexes was the
smaller commitment.

### What was given up, with the number

The native HNSW index. Semantic recall is now a cosine scan, which measured *faster* below roughly
5-6k embedded rows and slower above it - at 20k, 12.4ms with the index against 39.4ms without. Two
things bound the cost: the index engaged only in a `--features fastembed` build, and an ANN index is
a node-local recall aid exempt from the convergence norm (Principle 16, 4th revision), so adding one
back later changes no answer the graph must agree on.

On the read path the trade goes the other way: `graph` 9.91ms -> 5.64ms and `curation` 22.66ms ->
14.13ms at 800 observations, widening to 33.07ms -> 6.20ms on `graph` once rows carry embeddings,
because an f32 decode costs about 2ns per component against roughly 75ns to parse a JSON float.

### The refusal is what keeps a principle honest

Principle 3 demands that every encoding the log has ever used stays readable - append-only cuts both
ways, and a row that stops parsing is destroyed in effect. While one store held every era, that was a
permanent read shim inside the adapter. The store changed, so the demand moved rather than lapsed:
the older encodings are still readable by the release that wrote them, and this build makes skipping
that release fail loudly instead of starting empty beside a full store, which is the only way those
rows could actually be lost. The clause's evidence in the coverage registry now points at that guard.

### The port survived a backend replacement

`core` and `engine` did not change by a line while a third adapter was added and the original one was
deleted - a different query paradigm, a different storage engine, a different dependency tree. That is
the hexagonal claim stated as something that happened rather than something the diagram implies, and
the compliance ledger records it that way now.

What made it safe was moving the demands off the backend before removing it. The parity rules that
used to live in the Cozo adapter's own test module - traverse ordering, truncation, the dangling
endpoint, keyword alias reach - are cases of the port conformance suite, so deleting the adapter took
its tests and took nothing from the contract.

Registry: 72 clauses, 46 guarded and 3 structural, against 69/44/2 at v0.1.21. The P3 encoding
clause changed which guard it points at rather than losing one; the three added clauses are the
ingest refusal, the stored-log scan, and Principle 1's demand that no API write an unasserted fact -
that last one structural, because a test for it would have to enumerate callers that do not exist.

## Also

- The default store is `redb` and `SUPRAGNOSIS_DATA_DIR` defaults to `~/.supragnosis/redb`.
  `SUPRAGNOSIS_STORE` accepts `redb` (default) or `mem`.
- A daemon supervised by a unit file that passes no store argument will come up on the default. If
  you pinned `SUPRAGNOSIS_STORE=redb` during the opt-in period, it is now redundant but harmless.
