Changes since v0.1.21.

**Cozo is gone.** `redb` is the store - the only file-backed one - and the C++ RocksDB bridge that
came with Cozo is gone with it. Building supragnosis no longer needs `clang` or `libclang-dev`, on any
platform, and both CI workflows dropped the step that installed them.

This is a breaking change for an existing node, and the one thing to read before upgrading.

The rest of the release is mostly one theme: **the gate got the half of itself that was missing, and
the log got a door.** A merge can now be taken back, credential-shaped text is refused before it can
be appended, and the store handle the engine hands out can no longer write a fact into the graph
that never passed through an assertion.

## Upgrading from a Cozo store

**v0.1.21 is the last release that can read one.** This build refuses to start when it finds an
un-migrated Cozo store rather than coming up empty beside it, so the migration cannot be skipped by
accident - only postponed.

```bash
supragnosis stop
curl -fsSL https://supragnosis.dev/install.sh | sh -s -- --version v0.1.21
supragnosis migrate-store            # copies the log, then replays it
curl -fsSL https://supragnosis.dev/install.sh | sh   # back to latest
supragnosis start
```

Only the observation log is copied; the entity/relation graph is a projection of it and is rebuilt by
replay. The Cozo store is opened read-only and left untouched.

**Read [`docs/store-migration.md`](../store-migration.md) Section 5 first.** A replay reproduces
exactly what the log asserts and nothing else, which is correct and can look like data loss: rows
written into the projection outside the log - early-era direct writes, test fixtures - do not come
across. In the author's own store that was 72 entity rows out of 440. On a node whose knowledge
arrived through observe and federation it was zero. Check yours before switching; if any of it is
knowledge you want, re-assert it through `observe` first, which is where it should have been.

`migrate-store` is not in this release. The command belongs to the release that can still read the
format it migrates from, and doing otherwise would mean carrying the whole Cozo adapter forward to
serve a one-time act.

Also breaking, and quieter: the workspace declares `rust-version = "1.87"`. Nothing chose to raise
the floor - `int::is_multiple_of` had been in `core` undeclared since it was written, and trait
upcasting (1.86) is what makes the store port splittable. Declaring the floor at all is what made
clippy check it and say so. An older toolchain now fails naming the version instead of failing on a
coercion.

## Highlights

### A merge can be taken back

Principle 3's enforcement says "un-merge must be possible". Principle 15's says a wrong merge and a
wrong split are "both reversible". proposal-workflow.md names the third gated intent "entity-merge /
split". `PROPOSAL_KINDS` shipped five names with the split half missing, and it was tracked nowhere -
no clause in the coverage registry, no entry in the ledger, three documents demanding it.

So `entity_split` exists: it names the `entity_merge` proposal it reverses, and a merged one stops
that merge forwarding. The folded entities separate again, their relations point where they always
pointed, and the aliases the merge contributed come off.

Nothing is deleted to make that happen, which is the whole reason it is cheap. `merge_forwarding` is
the single thing every identity-touching read consults - ten call sites, none of which reads the merge
state directly - and the store port has no delete, so a merged-away row is still in the store and
filtered at read time, every time. The reversal is one edge ceasing to be contributed.

The part that needed care is the candidate loop. "Already merged" is *derived from the forwarding
map*, so removing the edge makes the pair a fresh high-similarity candidate: the console would
propose re-merging what a human just pulled apart, every time they looked at it. Both candidate
generators now read one suppression set rather than each learning what a split is, and the rule is
that a split suppresses the **suggestion** permanently and the **possibility** never - opening a
merge by hand stays allowed.

Two things [`docs/unmerge.md`](../unmerge.md) had wrong until the tests were written. A split cannot
require its target to be `merged`, because the check runs inside the fold that decides
merged-versus-blocked; it requires a merge verdict instead. And a re-merge has to be a
distinguishable proposal - that is not a design choice but content addressing, since re-opening a
reversed resolution verbatim yields the id the split already named, and the re-proposal would be
openable, verdictable and permanently unable to forward. `propose` refuses that and names the fix.

Reachable from the MCP `propose` tool and from an un-merge button on a committed merge in the
console. For scale: the author's node carries 58 merge proposals, 20 of them committed into 32 live
forwarding edges. Eleven were a reading of mojibake and ten were replayed in bulk during a workspace
re-key - which is to say the two categories most likely to be wrong were twenty-one of them, and
until now none of them could be undone.

### Credential-shaped text does not enter the log

Principle 17's fourth enforcement demand - a redaction hook at ingest - had no code and no clause.
Writing [`docs/excision.md`](../excision.md) is what surfaced it: specifying how a secret gets *out*
of an append-only log established that today it does not, which makes keeping it out the only
control that exists.

`observe` now refuses content that carries a credential shape - PEM private keys, AWS access key ids,
Google API keys, GitHub and Slack tokens, Stripe live keys, JWTs, URL-inline credentials. It refuses
rather than rewrites, and that is forced twice: Principle 1 forbids transforming an assertion before
the log, and a rewrite would move the content address (Principle 14) and dangle every reference. The
refusal names the shape and the field and never the value.

It runs at every local ingest door and deliberately **not** on the sync apply path. A detector's
patterns grow, so a newer node would refuse an event an older peer accepted, and the two would hold
different logs from one event set - the Principle 16 divergence that `apply` exists to avoid.

The same detector runs over the stored log as a curation signal, read-only like every other one, and
above the hygiene signals because this is not housekeeping. It reports the id, the field and the
shape, never the text: a report travels into logs and screenshots, and quoting the secret would copy
it everywhere the report goes. The door and the scan walk one shared field list, because two would
drift in the worst direction - a field the door checks and the scan does not is a secret reported as
absent.

`SUPRAGNOSIS_SCAN_SECRETS=0` turns off the **refusal**, not the report - the daemon warns at startup
when it is set, because a miss cannot be undone once an append-only log has replicated it. The
curation signal has no switch: it reads what is already there and changes nothing. In the author's own
log it found nothing, which is the answer you want and not one you can assume.

### The projection is unreachable outside the folds

Principle 1's third demand - "no API may write a fact that did not pass through an assertion directly
into the graph" - was a convention. The convention held: the whole workspace has exactly two calls to
the projection writes, both inside the folds.

What it did not hold against is the past. The author's store carries 35 entity rows that no
observation anywhere asserts, written directly in an era when something did reach for the handle.
They are invisible to the log, survive every re-projection, cannot cross the sync wire because there
is nothing to export, and a replay cannot reproduce them - which is exactly how the store migration
found them.

So the store port splits. `AssertionStore` appends to the log and reads the graph; `KnowledgeStore`
adds `put_entity`/`add_relation`. The engine holds the full trait and is now the only thing that
does, because `Engine::store()` hands out the narrow one - the sync crate applying replicated events,
the MCP tools and the CLI lose the ability by type rather than by discipline. Replicated knowledge
still lands through `apply`, which folds it the way observe does.

The evidence is structural rather than a scenario, and that is not a shortcut: a test for this clause
would have to enumerate callers that do not exist yet.

### Federation is managed from the console

A peer's shared workspaces can be narrowed from the viewer, which is the containment move that works
today - it stops a leak spreading, though it recalls nothing already synced. The admission list is a
live directory rather than a startup snapshot, so a change takes effect without a restart, and an
allowlist entry rejects unknown keys like every other config section (a typo in a peer's name used to
be silently ignored).

The viewer gained a settings dialog, reached from a gear in the status bar, with About and Peers as
tabs. Deliberately not on the MCP surface: peer administration is a sovereignty decision (Principle
17) and belongs to the local principal directly, not to an agent acting under their authority.

### Two folds that had drifted

`observe` and `reproject` now project relations through one fold. They had diverged: observe stamped
an edge with the attestation of the call that wrote it while reprojection used the authoring
attestation, so a replay could move an edge's trust tier with no change in the log. Entities already
ran one shared fold; relations were the half nobody checked.

And the T-Box is scoped to the workspace, including in the all-workspaces view, which is a union of
glossaries rather than one glossary. A type defined in one workspace was reaching another.

## Also

- **rustfmt.** The tree had never been formatted and nothing checked. `rustfmt.toml` is tuned to the
  density the code was already written at rather than to the defaults, which would have restyled it
  (`Hlc { wall, counter, node: node.to_string() }` becomes five lines under `struct_lit_width = 18`).
  Comments are untouched - every one of the 4528 comment lines in the tree at that commit came
  through byte-identical, checked before and after - because the prose is the point of them. `cargo fmt --all -- --check` is now a CI gate and a `task fmt`, and
  `.git-blame-ignore-revs` points at the pass so blame reads through it.
- **The landing page badge names the latest release**, not the workspace version. It read the
  workspace version until main moved ahead of the last tag, at which point the page advertised a
  version with no download behind it.
- `supragnosis-mcp` dropped a `tracing` dependency it never used - the only crate in the workspace
  declaring something it did not.
- The default store is `redb` and `SUPRAGNOSIS_DATA_DIR` defaults to `~/.supragnosis/redb`.
  `SUPRAGNOSIS_STORE` accepts `redb` (default) or `mem`.
- A daemon supervised by a unit file that passes no store argument will come up on the default. If
  you pinned `SUPRAGNOSIS_STORE=redb` during the opt-in period, it is now redundant but harmless.

## The Cozo removal, in detail

### What the Datalog was actually buying

Measured, not assumed. The adapter ran nineteen query shapes, of which exactly one was genuinely
recursive - `traverse`'s bounded BFS. The rest were point get/put on four relations, scans with a
workspace filter, a two-rule union for `relations_of`, and an ANN lookup. No time-travel operator
appeared anywhere. And the `query` passthrough has never been opened (Principles 12/21), so Datalog
was an implementation detail of one adapter rather than a surface anything else depended on.

Against that: Cozo's last release was 2023-12-11, and `cozorocks` was the only reason the build
needed a C++ toolchain. Replacing a query engine with a B-tree plus two secondary indexes was the
smaller commitment.

### What was given up, with the number

The native HNSW index. Semantic recall is now a cosine scan, which measured *faster* below roughly
5-6k embedded rows and slower above it - at 20k, 12.4ms with the index against 39.4ms without. Two
things bound the cost: the index engaged only in a `--features fastembed` build, and an ANN index is
a node-local recall aid exempt from the convergence norm (Principle 16, 4th revision), so adding one
back later changes no answer the graph must agree on.

On the read path the trade goes the other way: `graph` 9.91ms -> 5.64ms and `curation` 22.66ms ->
14.13ms at 800 observations, widening to 33.07ms -> 6.20ms on `graph` once rows carry embeddings,
because an f32 decode costs about 2ns per component against roughly 75ns to parse a JSON float.

### The refusal is what keeps a principle honest

Principle 3 demands that every encoding the log has ever used stays readable - append-only cuts both
ways, and a row that stops parsing is destroyed in effect. While one store held every era, that was a
permanent read shim inside the adapter. The store changed, so the demand moved rather than lapsed:
the older encodings are still readable by the release that wrote them, and this build makes skipping
that release fail loudly instead of starting empty beside a full store, which is the only way those
rows could actually be lost. The clause's evidence in the coverage registry now points at that guard.

### The port survived a backend replacement

`core` and `engine` did not change by a line while a third adapter was added and the original one was
deleted - a different query paradigm, a different storage engine, a different dependency tree. That is
the hexagonal claim stated as something that happened rather than something the diagram implies, and
the compliance ledger records it that way now.

What made it safe was moving the demands off the backend before removing it. The parity rules that
used to live in the Cozo adapter's own test module - traverse ordering, truncation, the dangling
endpoint, keyword alias reach - are cases of the port conformance suite, so deleting the adapter took
its tests and took nothing from the contract.
