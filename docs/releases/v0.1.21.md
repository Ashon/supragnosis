Changes since v0.1.20.

A second store. `redb` - a pure-Rust embedded B-tree with no transitive dependencies - now sits
beside Cozo behind the same `KnowledgeStore` port, and `migrate-store` moves a node's knowledge onto
it. It is **opt-in and reversible**: the default is still Cozo, the migration opens the Cozo store
and never writes to it, and going back is dropping a flag.

The reason is not preference. Cozo's last release was 2023-12-11, and the dependency that actually
costs is the one it carries - `cozorocks`, a C++ RocksDB bridge, which is why building supragnosis
needs `clang` and `libclang-dev` at all. What the Datalog buys was measured rather than assumed:
nineteen query shapes, of which exactly one is genuinely recursive, no time-travel operator used
anywhere, and a `query` passthrough that has never been opened - so Datalog was an implementation
detail of one adapter, not a surface anything else depended on.

No id-formula change and no change to what the log contains, so an existing node needs no migration
unless it wants one. Upgrade is the usual `brew upgrade`, then
`brew services restart supragnosis-server`.

The coverage registry now reads 69 clauses: 44 guarded, 2 structural, 2 pinned-but-unmet, 21
unmet-and-unpinned - one clause more than before, added because a defect found during this work had
no clause that would have caught it.

**Two things worth knowing before you migrate.**

- **A replay reproduces exactly what the log asserts, and nothing else.** On an existing store this
  is invisible, because `reproject` upserts and never deletes, so any row written into the projection
  outside the log survives every re-materialization. A migration starts empty, so those rows do not
  appear. In the author's own store that was 72 entity rows out of 440 - early-era rows written
  before the current ingest path existed. By Principle 1 they are not knowledge, since no assertion
  supports them. Check yours before switching:
  [`docs/store-migration.md`](../store-migration.md) Section 5.
- **Restart a stale daemon before comparing anything.** `brew upgrade` swaps the binary but does not
  restart a running daemon, and `--version` reports the binary rather than the process. A daemon up
  across an upgrade answers with older code, which makes a code difference read as a data difference.

## Highlights

### One conformance suite over the store port

The port states its contract in prose - absence is not failure, a response is reproducible, an
internal iteration order must not leak into a result - but it was checked per adapter, in each
adapter's own test module, with different cases and different counts. Cross-adapter parity existed
only where a divergence had already bitten. With a third adapter arriving, "the adapters agree" had
to become something a test says.

Seventeen cases now run against every adapter from one roster, covering absence across all eight
reads, the re-arrival absorb and its order independence, upsert-by-id, both directions of
`relations_of`, workspace scoping and alias reach in search, traverse direction/depth/truncation and
the dangling endpoint, the federation delta read, and semantic recall.

The first run failed one case: `InMemoryStore` returned its three enumerations in `HashMap` order
while Cozo, a B-tree, returned them by id. That divergence was known and declared - the P16 clause
names it - and the defence had been to prove no engine fold depends on the order. That defence holds
and stays. But the port now **promises** ascending id instead, because a hazard every consumer must
route around is worse than a promise the port keeps: "do not depend on the order" has to be re-proved
by each new reader of each new fold, while "rows come back by id" is proved once by everyone who
implements the trait.

### The redb adapter

Rows are JSON under their id - the same payload the Cozo `data` column holds - with multimap tables
as secondary indexes: workspace to id for the three enumerations, and from/to to relation id for
`relations_of` and the traversal's out-edges. Multimap values arrive sorted, so every read lands on
ascending id without sorting on the way out. `traverse` is an explicit BFS, which is the one thing
the recursive Datalog rule was for.

Measured on the read path (800 observations, release build): `graph` 9.91ms to 5.64ms, `curation`
22.66ms to 14.13ms. With vectors attached the gap widens to 33.07ms to 6.20ms on `graph` - an f32
decode costs about 2ns per component against roughly 75ns to parse a JSON float, which is most of
what was previously attributed to carrying embeddings through folds that never read them. `curation`
with vectors stays expensive on both (281.77ms vs 236.66ms): that is the O(E^2) merge band, and no
store change touches it.

### A dropped vector no longer looks like a backend without vectors

The first version of the redb adapter persisted rows by serializing them, and both embedding fields
carry `#[serde(skip)]` - deliberately, so hundreds of floats never ride out through the MCP surface.
So it accepted every vector and stored none.

The conformance suite did not catch it, and that is the more useful half of the story: a case written
to accommodate adapters that store no vectors skipped its assertions on an empty result, and "stores
none" reads exactly like "lost them all". Adapters now **declare** vector support and are held to it,
a round-trip case states the demand on its own - a ranking failure and a data-loss failure look
nothing alike from outside - and Principle 19 carries a clause for it.

Vectors now live in their own tables under a hand-rolled little-endian encoding, which is also what
makes the read path cheap: a fold that walks the log no longer parses 384 floats per row it never
looks at.

### Where the ANN index starts to pay

The one capability Cozo has and redb does not is the native HNSW index, so "is the older backend
still needed" reduces to that and to nothing else. Measured end to end rather than as isolated vector
math - a hit carries a snippet, so the row is fetched whichever way candidates were found:

| embedded rows | Cozo (HNSW) | redb (brute-force cosine) |
|---|---|---|
| 200 | 2.0ms | 0.3ms |
| 1000 | 3.9ms | 2.1ms |
| 5000 | 10.0ms | 9.5ms |
| 20000 | 12.4ms | 39.4ms |

The crossover is near 5-6k embedded rows. Below it the scan wins outright, because at that size both
are dominated by fetching rows and the scan is the one skipping an index to get there. Two bounds on
how much this matters: the index engages only in a `--features fastembed` build, and the prebuilt
binary ships `embed=none` with no semantic surface at all; and an ANN index is a node-local recall
aid exempt from the convergence norm, so giving redb one later changes no answer the graph must agree
on.

### The hexagonal claim, exercised

The Principle 12/20 ledger entry read as a claim about a shape: the store sits behind a port. It is
now a claim that was exercised - a third adapter was added without a line changing in `core` or
`engine`, and the port's contract is checked by one suite every adapter runs. That is the difference
between a hexagonal diagram and a hexagonal codebase, and the ledger is where the distinction belongs.

## Upgrade

```bash
brew upgrade
brew services restart supragnosis-server
```

Nothing else is required. To try the new store:

```bash
supragnosis stop
supragnosis migrate-store --dry-run
supragnosis migrate-store
supragnosis start --store redb
```

Read [`docs/store-migration.md`](../store-migration.md) first - Section 5 in particular if the store
predates v0.1.x.
