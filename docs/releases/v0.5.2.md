Changes since v0.5.1.

**Upgrade, then restart the daemon once; a demotion never raises a claim.** `brew upgrade`, then
`supragnosis restart`. The store, the sync protocol, the MCP tools and the prompts are unchanged.
Effective trust tiers are computed when they are read, so a store that holds a merged demotion which
asked for a higher tier shows its corrected tier after the restart; nothing is rewritten.

## A demotion never raises a claim, and a promotion never lowers one

A merged `claim_promotion` or `claim_demotion` sets a claim's trust tier through the gate. Each
granted `min(requested tier, the merging surface's ceiling)`, and the most recent merged one decided,
in either direction. So a `claim_demotion` that asked for a higher tier than its target held
**promoted** it when merged - from the console up to `human_confirmed`, from an agent up to
`host_signed` - and a demotion may be approved by the person who proposed it. A `claim_promotion`
that asked for a lower tier demoted. Principle 18 allows trust to rise only through an explicit
promotion, and this was a promotion under a demotion's name.

Now the merged gate events on a claim apply in the order of their merge verdicts, each from the tier
the previous one left: a promotion can only raise, a demotion can only lower. A demotion still pushes
a claim below the tier it started with, which is what contamination response needs. Every node
holding the same log computes the same tiers.

The belief diff a proposal shows in the Review panel now runs through the same rule. It used to
show the requested tier, so a reviewer could be shown a promotion where the fold would grant
something else.
