Changes since v0.2.0.

**Upgrade if you are on v0.2.0.** The guard that was supposed to stop a Cozo-era node from starting
empty beside its own data had a hole shaped exactly like the configuration most likely to walk into
it. Everything else here is the repository becoming something a stranger can use: a license, a threat
model, a container image, a Linux unit.

## The migration guard skipped the configuration that needed it

v0.2.0 refuses to start when it finds an un-migrated Cozo store, so that the migration can be
postponed but not skipped by accident. The shipped LaunchAgent set `SUPRAGNOSIS_STORE=cozo` and
pointed `SUPRAGNOSIS_DATA_DIR` at `~/.supragnosis/db` - both correct through v0.1.21, and both the
kind of setting nobody rewrites, because a working LaunchAgent is not something you revisit.

`refuse_unmigrated_store` returned early unless the store kind was exactly `redb`, so that
configuration walked straight past it. `build_engine` then opened redb anyway - it treats every kind
it does not recognise as redb - **inside the legacy directory**. A `knowledge.redb` appears beside
the RocksDB `CURRENT` marker: precisely the empty store next to a full one the guard exists to
prevent, reached through the guard rather than around it. The daemon comes up answering "nothing
here" for knowledge that is still on disk, and starts a second, divergent log.

The two functions disagreed about what counts as not-redb. The guard now keys on the same rule
`build_engine` uses - skip for the in-memory store, which touches no directory, and nothing else - so
a configuration naming a store this build dropped reaches the refusal with the migration instructions
it was always meant to print. The shipped agent names redb and the redb directory.

**If you already hit this**, the symptom is a daemon that answers as if the workspace were empty.
Stop it, check for `knowledge.redb` inside your Cozo data directory, delete that file (it is an empty
projection, not knowledge), and follow the v0.2.0 upgrade steps.

## Security

`rmcp` 0.16 -> 1.8, for **GHSA-89vp-x53w-74fx** (high): rmcp's streamable-http transport did not
validate the `Host` header before 1.4.0, so a malicious page could reach a loopback MCP server by DNS
rebinding and drive its tools.

**This daemon was not exposed.** `guard_local_origin` has refused non-loopback `Host` and `Origin`
since the transport was added, layered outside the rmcp service so it answers before the vulnerable
code runs, and `parse_loopback_addr` refuses a non-loopback bind in the first place. The upgrade is
defence in depth rather than a repair - which is the argument for doing it, since that guard standing
alone was never the intent.

`rust.yml` and `frontend-lint.yml` now declare read-only `permissions:`. Neither job writes anything,
and both hand their token to third-party actions - the toolchain installer, the cache, and in
frontend-lint's case `npm ci`, which runs whatever install scripts the dependency tree declares.

`SECURITY.md` is written as a threat model rather than an address, and states the known limitations
rather than leaving them to be discovered - starting with the MCP daemon being unauthenticated by
design as a local trust surface.

## The repository was legally closed

`Cargo.toml` declared `MIT OR Apache-2.0` and shipped neither text, so GitHub reported no license and
the legal default was all rights reserved: nobody could fork it, and the manifest was making a
statement about a file that did not exist. Both texts are here, with `CONTRIBUTING.md` beside them.

The hard part of CONTRIBUTING was `principles.md`. A 3000-line normative document presented as a
precondition turns contributors away, so it is stated as one review question - which clause does this
touch - with the note that making a principle unenforceable is a legitimate outcome as long as the
same PR amends it. What is refused is a change that quietly makes a declared clause false.

Crate manifests gained the metadata a crates.io publish needs and none of which was declared. The
license texts needed a second decision: cargo packages the workspace README by resolving the
inherited path but does not reach outside a crate directory for anything else, so the first packaging
run produced a `.crate` carrying an SPDX expression and neither file it names. Each crate carries a
symlink, which is what the ecosystem already does.

## Deploying a hub

Two new targets, both written against a real hub rather than from the manual.

**A systemd user unit** ([deploy/systemd](../../deploy/systemd/)), because federation.md Phase 6 calls
for deploying a hub behind one and there was no unit to deploy - `deploy/` held launchd and Homebrew,
both macOS. A *user* unit: the store, the node key and the config all live under `~/.supragnosis`, so
nothing needs root, which matters because the always-on box that makes a good hub is often one you
hold only password sudo on. Two things bite specifically in a user unit and both fail quietly:
`StartLimitIntervalSec`/`StartLimitBurst` belong in `[Unit]` or the crash-loop guard silently does not
exist, and the `ProtectKernel*` hardening a system unit takes for granted kills a user unit with
`218/CAPABILITIES` before it runs.

**A container image** ([deploy/docker](../../deploy/docker/)), which is the shape a hub wants and the
wrong shape for a personal node - the viewer and MCP surfaces are local-only by design, and a
container has no local. Two properties decide whether it works, so both are configuration rather than
prose: the node key is written once and the `node_id` derives from it permanently (F14), so the volume
is not a convenience - measured, a named volume gives the same id across recreate and no volume gives
a different one on the first restart, which is not a restarted node but a retired one. And redb takes
a single lock, so `replicas: 1` carries a comment about why a start-first update order corrupts rather
than races.

Port 7373 is deliberately not published. The MCP daemon is unauthenticated by design as a local trust
surface, so publishing it from a container puts an unauthenticated *write* surface on the network -
the one difference between a loopback bind on a host and a port mapping that makes the same code
dangerous.

## Also

- **The declared MSRV was false and is now tested.** It read 1.87 and was wrong the day it was
  written: clippy's `incompatible_msrv` lints this workspace's own code and never the dependency
  graph, and CI only ran stable. The floor is 1.95, set by `oxc` - a build-dependency of
  supragnosis-viz that minifies the viewer assets in release builds - with `darling` at 1.88 through
  rmcp-macros. A `msrv` job now builds at whatever the manifest declares, so the number cannot drift
  back into being aspirational.
- **The desktop shell is its own workspace.** It shares no code with the server: it owns no engine
  and no store and reaches the daemon over a unix socket, a process boundary rather than a link
  boundary. Membership cost one dependency graph - 111 Tauri packages sat in the server's lockfile,
  where an advisory against a webview dependency reads as an advisory against the daemon. The
  lockfile goes from 787 packages to 571 and no longer contains tauri, wry or webkit. The version now
  lives in two manifests and moves in one commit.
- The `propose` tool description no longer restates its own parameter schema, and `tbox_change` and
  `recall` are explained rather than listed - two of the six kinds had no gloss anywhere on the
  surface, so an agent could see they existed and had no way to learn what they did.
- The single-writer rule is attributed to redb rather than to the Cozo and RocksDB that used to
  enforce it. The rule survived the store swap; the reason given for it had not, and those are the
  lines an operator reads at the moment `task dev` refuses to start.
- The landing page still described the store it replaced.
