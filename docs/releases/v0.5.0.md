Changes since v0.4.12.

**Apple silicon and glibc 2.39+ only; then fetch the model once and reproject existing knowledge.**
`brew upgrade`, `supragnosis restart`, `supragnosis embed fetch` (224 MB, once; `service install`
does it for a new install), and `supragnosis reproject` with the daemon stopped, so what you already
know gets vectors. The store format, the sync protocol, the MCP tools and the prompts are unchanged;
two CLI commands are new and two JSON answers gain a field under the same schema number.

## v0.4.12 was the last release for Intel Macs and for Linux before glibc 2.39

The macOS binaries and the app are built for Apple silicon only. On an Intel Mac `brew upgrade`
refuses the formula and the cask on the architecture, and `install.sh` says so before downloading
anything; the way to v0.5.0 there is a source build
([deploy/homebrew/README.md](../../deploy/homebrew/README.md)). A shell running under Rosetta on
Apple silicon still gets the arm64 binary.

The Linux binaries are built on Ubuntu 24.04 and need glibc 2.39 or later: Ubuntu 24.04, Debian 13,
Fedora 40 and later. The embedding model's runtime set that floor
([docs/semantic-retrieval.md](../semantic-retrieval.md) Section 4): the static ONNX Runtime the
binary links was compiled against glibc 2.38 and GCC 13's libstdc++, which Ubuntu 22.04 cannot
link, and a build on 24.04 asks for 24.04's glibc. On an older host `install.sh` refuses with the
reason, and a `brew upgrade` there installs a binary that does not start (`GLIBC_2.39 not found`).
The ways out are a source build ([deploy/systemd/README.md](../../deploy/systemd/README.md)) or the
container image, which carries its own glibc and its own copy of the model.

## Semantic retrieval ships in the prebuilt binary

Every release until now was keyword only: `search_knowledge` matched every term of the query, and a
question phrased with other words found nothing. Measured before this change, a paraphrased
question found its target 0 times in 6, in Korean and in English alike.

The binary now carries the ONNX runtime, and the first `observe` or `search_knowledge` loads a
local embedding model: paraphrase-multilingual-MiniLM-L12-v2, quantized, 384 dimensions. In the
same measurement it put the target first 3 times in 6 for Korean and 4 in 6 for English, with the
target in the top three 5 and 6 times. `search_knowledge` answers label the mode, `hybrid` or
`keyword`, as they did.

What it costs, and what to know:

- **The model is fetched once, 224 MB, by `supragnosis embed fetch`.** `service install` runs it
  after the job is in, and the desktop app's Start at Login goes through the same command. The
  daemon never downloads: until the files are there, retrieval is keyword only, every answer says
  so in its `mode`, and `supragnosis status` says `semantic off` with the command to run. After
  the fetch, a running daemon picks the model up on its next embed; no restart is needed.
- **Loaded, the daemon holds about 1 GB** (it was 16 MB). The model loads on first use, so a
  daemon nobody asks stays small. `SUPRAGNOSIS_EMBED=none` keeps a node keyword only and small,
  which is what a pure federation hub wants.
- **`SUPRAGNOSIS_EMBED_MODEL=bge-small-en`** picks the English-only model instead: 129 MB, about
  290 MB resident, and no use on Korean. Any other value is refused at start naming both.
- **Knowledge written before this release has no vectors.** `supragnosis reproject` (daemon
  stopped) gives every entity one; observations written before stay findable by keyword. The
  store records which model embedded it and refuses to reopen under another, so switching models
  means a new `SUPRAGNOSIS_DATA_DIR`.
- The model lives in `~/.supragnosis/models` (`SUPRAGNOSIS_MODEL_DIR` moves it), inside the state
  directory, so removing that directory still removes everything. The container image has the
  model baked in at `/usr/share/supragnosis/models` and is about 400 MB.
- On Linux the binary asks the host for glibc alone: libstdc++ is linked statically and the
  release checks what the binary links on every build.

## A commit asks the agent for the decision behind it

Principle 22 says knowledge is a by-product of work; until now whether an agent called `observe`
during a task depended on the instructions it had been given. `supragnosis connect claude-code`
now also registers a hook in Claude Code's settings (`~/.claude/settings.json`), and the hook does
two things, with the person asking for neither:

- **After a commit the agent made**, it hands the agent the commit's id, subject and author with
  one question: if this settled a decision, a constraint or a fact about the project that the
  diff does not show, record it now with `observe` in the repository's workspace; if nothing,
  record nothing. A commit that failed, or one made minutes earlier by someone else, gets no
  question.
- **At a session's start**, it says what the repository's workspace holds on this node, or that it
  is not known here yet and the first `observe` creates it, so the agent searches before it
  assumes.

The hook never blocks and never writes anything itself; the agent decides, through the bridge, as
for any `observe`. Run `supragnosis connect claude-code` again on a machine already connected to
get it; `--no-capture` registers the bridge alone, and `connect --remove claude-code` takes both
out and gives the settings file back as it was. `connect` and `connect --json` say `capture on` or
`off` beside the entry, and the app's Claude Code row does too
([docs/client-connect.md](../client-connect.md) Section 12).

## Also

- The site, its link-preview card and the repository description say what the README says:
  memory for AI agents that remembers who said it.
- Dependencies: rustls 0.23.46, for RUSTSEC-2026-0346 to 0349 (TLS secrets in `Debug` output,
  buffered data after an ECH rejection, a 1 GiB brotli allocation before authentication, a
  downgrade to classical key exchange). fastembed is taken over rustls alone, so the Linux binary
  links no OpenSSL.
- The container image builds each architecture on its own native runner and joins them into one
  manifest; the v0.4.12 release run spent 76 minutes on the arm64 half under QEMU.
- A sync pull encodes only the page it sends, not the whole delta behind it; the first sync of a
  large workspace used to cost the square of its size in serialization.
- A peer's hybrid logical clock stamp with a full counter carries into the next wall instead of
  overflowing, which panicked a debug build while holding the sync node's clock and wrapped to the
  past in a release build.
- The hub's read tier audits by the grants a principal has, not by the workspace name a request
  invents, so an admitted principal cannot grow the hub's memory and logs by guessing names.
- MCP resource reads and viewer requests run on blocking threads, as the tools' store work does; a
  large workspace's graph no longer holds an async worker and queues the requests behind it.
- `connect` refuses a client configuration it cannot read instead of rewriting it as empty; the
  console's narrowing of a peer narrows every allowlist entry it has and writes the file
  atomically; a request the daemon leaves unanswered reaches the client as an error, not silence;
  a hub whose listener cannot start stops the daemon instead of running on without one;
  `reproject --help` and `migrate --help` describe the option they have.
- Documents: how a stamp's HLC orders the log alike everywhere and is causal only as far as clocks
  agree; how to remove supragnosis and what removal leaves; the systemd guide's install without a
  checkout and its C compiler note; the viewer proxy's six writes to refuse.
