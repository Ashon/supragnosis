Changes since v0.4.0.

**Upgrade if you read resources.** Every one of them is unreadable on an MCP client that validates
the response envelope - the client connects, authenticates, lists the resources, and then gets a
schema error instead of the bytes. The tools are fine. This is v0.3.1's defect in the one method
v0.3.1's guard did not walk.

## The same two fields, one method further down

A current Claude Code client answers a read with:

```
Invalid result for resources/read:
  ["ttlMs"]      expected number, received undefined
  ["cacheScope"] expected one of "public"|"private"
```

v0.3.1 has this error in it already, under `tools/list`, with four paragraphs about why the two
SEP-2549 fields have to be emitted whatever the negotiated version says. It took over
`list_tools`, `list_resources` and `list_resource_templates` from the macro and gave each of them
`ttlMs: 0` and `cacheScope: private`. It did not touch `read_resource`, which was hand-written
already and had never had them.

So the surface has been half-fixed since v0.3.1: a client could discover every resource and read
none of them. `ttl_ms` and `cache_scope` are `Option` with `skip_serializing_if`, so the fields are
not wrong on the wire, they are absent from it, and the client rejects the whole response rather
than the field. That is the same reason v0.3.1 gave for why this reads as a broken server: the
message names a cache field, so nothing about it says "the resource is there and you cannot have
it".

The fix is one line, and where it goes is the point. Each of the five URI forms - `workspaces`,
`graph`, `hypergraph`, `types`, `observation` - builds its own result, so five branches could each
have gained the hints. They are applied instead at the single place where a read becomes a
response, because the defect being repaired is exactly "a method that did not get the treatment
the others got". Five copies of a hint is five chances for a sixth resource to miss it.

## The observation resource looks like the exception and is not

`ttlMs` is 0 on every branch. Four of them need no argument - the graph, hypergraph, types and
workspace list all change on the next `observe`, and v0.3.1 already recorded why a freshness window
on a growing list is a window in which a client is told a workspace does not exist.

`supragnosis://observation/{id}` is the one that invites a real TTL. An observation is immutable by
Principle 3: it is superseded, never edited, so its *content* at a given id will never differ. Its
*payload* is not immutable. `Observation::provenance` is a monotonic union - the same content
arriving from a second host is absorbed as another attestation rather than overwriting the first -
and the trust tier inside each attestation moves under `claim_promotion` and `claim_demotion`.

That makes caching this one resource worse than caching the others, not better. A caller fetches an
observation to confirm the basis of a search hit: who attested it, at what tier, derived from what.
Those are the fields that move. A cached read would serve the content correctly and the basis
stalely, which is the failure this resource exists to prevent.

## Why it stayed hidden for a release

Not an unrestarted daemon this time - v0.3.1's own explanation, and the reason it noted that one.
This one is simpler: reads are rare. An agent asks for tools on every connection and for a resource
only when something actually wants the whole graph, so the broken half of the surface is the half
nobody exercises by accident.

It surfaced during an ontology audit, on a request for a full workspace graph in one read rather
than one `get_entity` per node. The fallback worked - the per-entity path is a tool call, and tools
were never broken - which is also why the report reached "the resource read fails" rather than "the
server is down".

Guarded now by `every_resource_read_carries_cache_hints`, which drives a real client over the
in-process pipe like its list-side sibling, and walks all five URI forms so a sixth cannot arrive
without hints. It fails with `left: None` if the one-line change is removed, so it holds the fix
rather than restating it.

## Also

- `every_list_result_carries_cache_hints` keeps its name and its scope. The two tests are separate
  because a list and a read are separate methods on the server, and the lesson of this release is
  that a guard named after one of them does not cover the other.
