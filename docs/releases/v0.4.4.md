Changes since v0.4.3.

**Upgrade, then restart the daemon once.** The first start of v0.4.4 re-projects every workspace
before it serves - a one-time repair for writes an earlier version may have left half-applied - and
closes `~/.supragnosis` to other accounts. On the author's store that took a few seconds, and
`supragnosis status` reports it. `brew upgrade` then `supragnosis restart` (or Restart Daemon in the
tray); nothing else to do.

The store gains one table and the sync protocol is unchanged. The MCP surface gains one field:
`sync_push` reports a re-projection when it stamped anything. This release also carries the
container image that v0.4.3 failed to publish.

## A crash between writing and showing no longer loses what was written

`observe` appends to the log in one store transaction and projects the graph in one transaction
per row, and nothing tied the two together. A process that ended in between left knowledge the log
held and the graph did not show. In the review that found it, eight SIGKILLs during `observe` left
8 of 23 observations partly unprojected. `get_entity` answered "not found" for entities the log
asserts, and nothing noticed. That is an ordinary event here, not an exotic one: the desktop shell
stops the daemon it spawned with SIGKILL, and the daemon has no SIGTERM handler, so a launchd stop
ends it at once.

Specified first in
[docs/crash-recovery.md](https://github.com/Ashon/supragnosis/blob/main/docs/crash-recovery.md):

- **Every append records that its projection is owed, in the append's own transaction.** The store
  does this, so every path that writes the log does it, including the sync crate.
- **Entries are cleared by the projection that repays them.**
- **A process that opens the store repays what is owed before it binds a socket.** Correctness no
  longer depends on how a process ends.
- **Recovery is reported, not only logged.** The viewer's new `/api/health` and `supragnosis status`
  say what was recovered and how many projections are still owed.
- **Upgrading repairs the past too.** A store the ledger has never seen has no record of what was
  projected, so the first open by v0.4.4 counts every row as owed and re-projects each workspace
  once. On a copy of the author's store this re-projected 201 observations across three workspaces,
  and the graph came out identical, 336 nodes and 548 edges.

Building it found one place the graph was already behind its log, unreported. A hub stamps its own
rows when a peer pulls, stamping rewrites rows the projection carries, and only pushes
re-materialized. Pulls that stamp now re-materialize as well.

## The lifecycle commands, tested against running processes

v0.4.3 gave the daemon one manager. Testing that against real processes found five places where
the built behavior fell short of its own rules
([daemon-lifecycle.md](https://github.com/Ashon/supragnosis/blob/main/docs/daemon-lifecycle.md)
Section 11):

- **A stdio server was invisible.** It holds the store and binds no port, so
  `supragnosis service install` started the login job beside it, and that job crash-looped on the
  lock. The CLI now probes whether the store is held, using a read-only open that redb refuses while
  a writer has the file. A store held by nothing the CLI manages is refused, with or without
  `--take-over`. The same refusal covers the desktop app's own daemon.
- **A stale pidfile could aim SIGTERM at an unrelated process** that had inherited the pid. A pid
  now counts only when it is a supragnosis executable.
- **`--env SUPRAGNOSIS_MCP_AUTH=off` produced a login job without authentication.** `install` now
  refuses an environment that disables auth or the secret scan, or names a non-loopback address,
  whether it was given or carried over from a replaced plist.
- **`install` and `restart` reported success for a job that never came up.** They now wait for the
  daemon to answer. When launchd shows the job failing, they exit non-zero and name the log.
- **`status` printed the bearer token**, and agents run `status`. It now prints where the token is,
  and a connect line that reads it with `$(cat ...)`.

## `~/.supragnosis` is closed to other accounts

The documentation said the token, the node key and the store live "in the 0700 `~/.supragnosis`
dir". On the author's machine the directory was 0755 and the store file 0644. Any other local
account could have copied the whole store without needing the token.

- Every writing process now closes the directory on start.
- Secrets are created 0600 instead of chmodded after being written.
- The desktop shell creates the directory 0700.
- The systemd unit sets `UMask=0077`.

## The container image is back

v0.4.3 published binaries, the desktop app and the Homebrew tap, but no image: the Dockerfile still
built with `rust:1.95` after the declared floor moved to 1.96. Its comment said the msrv CI job kept
the two together, but that job never read the Dockerfile, and the Dockerfile builds only at release.
The pin is now 1.96, and a test holds it equal to `rust-version` on every push.
