Changes since v0.6.4.

**Upgrade the server, then restart once; `supragnosis setup` takes a first run to its first entry.**
`brew upgrade`, then `supragnosis restart`. The store, the sync protocol and the MCP tools are
unchanged; `status --json` gains a field and keeps its schema number. The app is only rebuilt with
the version: its Welcome page, which will draw the same steps, is not in this release.

## `supragnosis setup`

No install path connected an AI app, kept the daemon running past the app's own session, or fetched
the search model, and the steps that did were printed by the installer and gone by the time anyone
looked for them. `supragnosis setup` reads where this machine stands and does what is not done, in
four steps: keep the daemon running at login, connect the AI apps that are installed, download the
search model, and wait for the first entry the person's own work makes. It shows the plan and asks
before it changes anything; `--check` only reads, `--yes` applies the defaults, `--step` applies one
step, and `--events` writes JSON lines for the app.

Each act runs the same command a person would - `service install`, `connect`, `embed fetch` - and
says what it ran and which files it changed. Setup takes over only a daemon nobody chose a manager
for (one `supragnosis start` ran, or a login job an earlier release installed). A Homebrew service,
a hand-written plist or a process it cannot name is left alone: counted as done while it keeps the
daemon answering, and otherwise reported with the command that would act. It writes nothing to the
store: the last step suggests something real to ask a connected app, and waits. On Linux it installs
no service yet and names the unit to copy. The procedure is docs/onboarding.md.

## The daemon knows which apps have reached it

When an AI app starts a session, the daemon now notes the name the app gives itself, in memory only,
and serves the list on its local socket and as `clients` in `status --json`. It is how setup can say
an app reached the daemon without writing anything to find out. A hub's read tier refuses it, a
hub's listener for principals records nothing, and a restart forgets it.

## A half-downloaded model is missing, not broken

The check for the search model counted any file over a megabyte, and a download in progress leaves
one. A daemon that searched while `embed fetch` was still running, or after a fetch was interrupted,
tried to load a model that was not all there, and when that failed it stayed on keyword search until
it was restarted. The model is now present only when the cache links every file it needs, so a
partial download reads as missing, and the daemon loads the model on the first search or write after
it is complete. `embed fetch --events` reports the download's progress for the app.

## Also

- `connect` names the file it wrote or the command it ran, and says so when no server answers: the
  entry is written, and the app fails until one runs.
- `status` on a stopped machine says how to start the daemon, how to keep it running, and
  `supragnosis setup`.
- The `brief` prompt says when a workspace holds nothing yet, and names the workspaces that do,
  instead of handing the model a page of zeros to interpret.
- The install script ends with `supragnosis setup` and offers to run it.
- `service install --no-model` leaves the model to `embed fetch`.
- The README shows line coverage, measured on every push to main.
- Two TLS tests that sometimes failed together on macOS no longer share a temp directory.
