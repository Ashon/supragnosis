Changes since v0.4.6.

**Upgrade, then restart the daemon once; the app's settings moved.** `brew upgrade` then
`supragnosis restart`, as after any release. The desktop app's tray now holds a status line, Open
Graph, Settings... and Quit. Start at Login, Restart Daemon, the server and the AI apps moved to a
Settings page, which the graph's gear opens. From this release on, installing the app on Apple
silicon no longer asks for Xcode. The store, the sync protocol and every client configuration are
unchanged.

## Installing no longer asks for Xcode

The app's cask depends on the `supragnosis-server` formula. That formula only copies the release's
prebuilt binary, but it had no bottle. Homebrew treats a formula without a bottle as a source build,
and before installing one it requires an up-to-date Xcode or Command Line Tools, though nothing is
compiled. So installing the app asked for Xcode.
([deploy/homebrew/README.md](https://github.com/Ashon/supragnosis/blob/main/deploy/homebrew/README.md),
Bottles)

- **The formula is bottled.** Each release now builds the bottle the standard way (`--build-bottle`,
  then `brew bottle`), reinstalls from it, and requires that Homebrew poured it before attaching it.
  Homebrew pours a bottle without the source-build checks.
- **Who gets one:** Apple silicon on macOS 14 or later, and x86_64 Linux. Intel Macs keep the
  source-build path: the release cross-compiles the Intel binary, and there is no Intel machine to
  bottle it on.
- **A check guards it.** A workflow bottles the latest release whenever the formula or its renderer
  changes, and weekly, so a change that breaks bottling shows up before a release depends on it.

## A Settings page in the app

The tray could switch and toggle, but it could not take input. Adding a server on another machine
still meant a terminal, and every outcome was appended to one status line.
([docs/settings-page.md](https://github.com/Ashon/supragnosis/blob/main/docs/settings-page.md))

- **It opens from the graph's gear**, at the right end of the status bar, where settings have always
  been. Cmd+, opens it too, and the tray's Settings... opens it at the section that needs attention.
  It closes back to the graph with its x or Esc, or Cmd+1.
- **Its sections:**
  - **Server**: use, remove, and add a server. A credential is handed to the CLI on stdin, never put
    in an argument.
  - **AI apps**: each app's state, and one button that says what a click will do.
  - **This Mac**: the daemon's state, Start at Login, Restart, and the store's health.
  - **Sync**: this node, the hubs it syncs to and, on a hub, what each peer may read - with the
    console's one act, stop sharing a workspace, behind a confirmation.
  - **About**: the versions, paths, license and source.

  The viewer's own dialog, which the gear used to open, became Sync and About here, so the app has
  one place called settings.
- **Only this page can change a setting.** The main window also shows the viewer, which a daemon -
  and later a hub on another machine - serves. Every settings command is closed by default, and
  each one refuses unless the window's top-level page is the app's own Settings page.

## The hub serves its viewer to its principals

Step 1 of [docs/remote-viewer.md](https://github.com/Ashon/supragnosis/blob/main/docs/remote-viewer.md),
federation's read tier. A hub now serves the viewer at `/viz/` on its sync listener, to the
principals it already admits at `/mcp`:

- **It is read-only, and every path has a declared policy.** Verdicts, the console's other writes
  and the node's own operations are refused, with where to do them instead.
- **Every workspace resolves against the reader's grants.**
  - Enumeration lists only the grants.
  - `*` is the union of the grants, each projected alone.
  - A union that includes a workspace the hub may not serve is refused as a whole, naming why.
  - An id outside the grants reads as an unknown one.
- **The event stream carries knowledge, not activity:** observes in the grants, without their
  sessions.

The desktop app does not browse a remote server yet. That needs the relay and the app's side
(steps 2 and 3).
