Changes since v0.2.2.

**The HTTP daemon now requires a bearer token, and this breaks every client already connected.** An
existing `claude mcp add --transport http` entry starts answering 401 on upgrade. The way back is
printed where the break is noticed: `supragnosis start` prints the full command, and `status` prints
it again for a daemon that is already running.

```
Authorization: Bearer $(cat ~/.supragnosis/mcp.token)
```

`SUPRAGNOSIS_MCP_AUTH=off` drops the check for a single-user box.

## Why loopback was not enough

`parse_loopback_addr` refuses a non-local bind and that guard is real, but it answers a different
question than the one Principle 17 asks. Loopback is host-local, and P17 says stdio, single user. On
a multi-user machine every local OS account could reach the whole tool surface through
127.0.0.1:7373 - observe, review, sync_push, workspace enumeration, a `search_knowledge` with no
workspace scope. P17 held for the stdio transport and never for this one.

architecture.md carried this as an overdue M4 entry condition with two named routes out: a unix
socket, or an auth layer. The socket is not available here, because MCP clients reach the daemon at
`http://127.0.0.1:7373/mcp` and `claude mcp add --transport http` cannot speak one. So the
confinement moves from the socket to a secret, and the secret keeps the property the socket had:
`~/.supragnosis/mcp.token`, 32 bytes of entropy, mode 0600, inside the 0700 directory. One OS user,
enforced by the OS - the same answer the viewer got, carried by a different file.

`status` reads the token and never generates one. A missing file there is the honest report that
this daemon is running without auth, rather than an invitation to mint a token it is not using.

What is NOT repaid, and stays recorded: a single-user gate is not a per-principal one. When
federation Phase 3.5 opens the authenticated network read tier, workspace enumeration and
`workspace=*` must be filtered by that user's grants rather than admitted wholesale to whoever holds
the local token.

## A content-security-policy, and the proxy that was dropping it

Output escaping is the viewer's first defence against stored XSS and it is guarded twice. But the
page renders entity names, descriptions and proposal rationale, which under federation are synced,
attacker-influenceable input - so one missed `esc()` is code execution on a surface that can observe,
review and un-merge. One escape is one mistake away from being none.

Every response now carries a policy, and `script-src` is strict rather than decorative: viewer.html
loads its script with a src and carries no inline `<script>`, so nothing needs `'unsafe-inline'` and
an injected `<script>`, an `onclick=` attribute and a `javascript:` URI are all refused.

The desktop shell's half mattered most and was easiest to miss. Its `viz://` proxy forwarded
content-type and cache-control and dropped everything else, so the surface a human actually looks at
was the only one getting no policy at all.

## The supply chain caught up

Nine dependency updates, and one of them is not mechanical. **rmcp 3** merges the raw-struct plus
`Annotated<T>` pair into a single `Resource` that carries annotations as an ordinary field, removes
`no_annotation()`, makes both resource types `#[non_exhaustive]` (so the templates are built rather
than declared), and returns `ReadResourceResponse` from `read_resource`. The protocol tests drive a
real client and pass unchanged, so the wire format did not move.

thiserror 2 folds a 1.x/2.x split in the lock back into one version. toml_edit 0.25, pulldown-cmark
0.13, and a patch group of serde, serde_json, anyhow, tokio, rustls and clap. Five GitHub Actions
majors.

## The gate that could not see its own configuration

`RUSTSEC-2026-0235` entered the advisory database on 2026-08-04 and turned the supply-chain gate red
on a tree that had not changed. `rkyv` 0.7.46 is reached only as lightningcss -> parcel_sourcemap ->
rkyv, and lightningcss is a build-dependency that minifies this repository's own CSS - the advisory
names untrusted archives as the risk, and the only archives here are the ones the build makes from
assets sitting beside it. Upstream fixed it in 0.8.17 and dropped the 0.7 series, so it closes when
lightningcss moves majors, which is not a version this project picks. Ignored with that reasoning
written down, and `deny.toml`'s claim that a vulnerability never gets an ignore rewritten to say what
the exception is and what still gets none.

Fixing that exposed a second thing. `rust.yml` filters on paths and `deny.toml` was not one of them,
so the job that reads the supply-chain configuration never ran when the configuration changed: an
allow list could be widened, or an advisory ignored, and nothing would check the result until an
unrelated push to `crates/` happened to land. It surfaced because the commit that edited `deny.toml`
got no cargo-deny run at all.
