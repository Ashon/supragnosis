Changes since v0.3.0.

**Upgrade if you are on v0.3.0.** Its tool list is invisible to any MCP client new enough to
validate the response envelope - the client connects, authenticates, and then discards all thirteen
tools over two absent cache fields. Everything else here is repair work on the paths that were
supposed to catch exactly that: a release dry run that could never finish, a dev task copying a
store deleted four releases ago, and a CI gate that had gone red on its own.

## Thirteen tools behind two missing fields

A current Claude Code client answers:

```
supragnosis: http://127.0.0.1:7373/mcp (HTTP) - ! Connected · tools fetch failed
  Invalid result for tools/list:
    ["ttlMs"]      expected number, received undefined
    ["cacheScope"] expected one of "public"|"private"
```

It connects and it authenticates. This is not v0.3.0's bearer token. The entire tool surface
disappears at once, and the message names a cache field rather than the surface, so nothing about it
reads as "the tools are gone".

`#[tool_handler]` generates `list_tools`, and the version it generates gates the two SEP-2549 fields
on the negotiated protocol reaching 2026-07-28 - the version rmcp's own field documentation calls
them required at. This client negotiates 2025-11-25 and validates them anyway. Whether the client is
early or the library is late does not decide what to do: 2026-07-28 owes those fields regardless, so
emitting them is work that has to happen, and it is the only version of that work that also unblocks
the client today. The macro generates the method only when the impl does not define one, so this
takes it over rather than patching around it.

Both values are chosen rather than inherited. `ttlMs` is 0 - do not treat this as fresh - which is
what rmcp hands a 2026-07-28 client. The tool list is fixed at compile time, so a freshness window
buys nothing and would let a client keep serving a list from before an upgrade that added a tool.
On `resources/list` that zero stops being merely safe and becomes required: the resource list grows
with the workspaces, and any window is a window in which a client is told a workspace does not
exist. Principle 5 draws that line on the read path and a cache would move it back.

`cacheScope` is `private` where the generated version says `public`. The list is identical for every
caller, but reaching it needs this node's bearer token, and Principle 17's argument for that token is
that loopback confines the surface to the host rather than to one user. Labelling a token-gated
response shareable across authorization contexts contradicts the reason the token exists.

How it stayed hidden is the part worth recording. The machine that found it was running a daemon
started four days before v0.3.0 existed and never restarted since - an old binary, negotiating an old
protocol, working fine while the binary on disk did not. Anyone installing v0.3.0 fresh hit this
immediately. Guarded now by `every_list_result_carries_cache_hints`, which drives a real client over
the in-process pipe.

## The release dry run could never go green

This file's own header offers `workflow_dispatch` as the way to exercise the release pipeline
without cutting a release. Triggered for the first time, it failed - on the one job the dry run
exists to prove.

`derive tags` computes the version as `${GITHUB_REF_NAME#v}`. On a tag that is the release; on a
dispatch it is the branch name. So the server.json check compared `ghcr.io/ashon/supragnosis:main`
against the `0.3.0` the manifest names and exited 1, after the container job had already built both
architectures successfully. The comparison is sound and its input never could be.

It is tag-guarded now, like every publish step in that file and for the same reason.
`manifest_consistency.rs` already holds server.json equal to the workspace version on every push,
and the half that genuinely needs a tag still runs on every tag. The header also claimed more than
it delivered: a dispatch reaches neither the Release, ghcr, nor the tap, but it does submit the
bundle to Apple's notary service, because the signing step is gated on the secrets existing rather
than on the ref. That is the right default - a dry run that skipped notarization would not prove the
step that breaks most often - and it now says so.

## dev:snapshot was copying a store deleted in v0.2.0

`task dev:snapshot` describes itself as "a COPY of the live daemon's knowledge - real data". Its
`LIVE_DATA` pointed at `~/.supragnosis/db`, the pre-0.2 Cozo directory, four releases after redb
replaced it.

The failure was silent, which is what makes it worth a line here. The copied directory holds no
`knowledge.redb`, so the dev daemon does not refuse to start and does not report a missing store -
it creates an empty database and serves an empty graph. The un-migrated-store guard would have
caught a Cozo directory at the real path; it does not fire here because the copy arrives under a dev
path. Measured against the real store: the old path served 0 nodes, the corrected one serves 168.

The RocksDB crash-consistency argument above that task went with the engine that justified it. Its
replacement does not pretend the old reasoning transfers - redb is one file, and `cp` can read a
page the writer has already moved past, so a copy can be torn in a way a power cut is not. What
makes it acceptable is that redb refuses to open a file whose commit slot and pages disagree, so a
bad copy is a loud startup error rather than a quietly short graph. Three stale references in
`deploy/` moved with it.

## The gate had gone red without the tree changing

Two failures arrived on an unchanged repository, six days apart, and blocked eleven dependency
updates behind them.

Rust 1.98 added `clippy::chunks_exact_to_as_chunks`, and this workspace denies `clippy::all`, so
every push touching `crates/**` failed on `decode_vector`. Replacing `chunks_exact` with `as_chunks`
changed what the length guard above it does: `chunks_exact` leaves a trailing partial chunk
reachable through `remainder()`, while `as_chunks` drops it the moment you take `.0`. The
`is_multiple_of(4)` check stopped being a defensive early return and became the thing keeping a
corrupt row from decoding to a short vector and being used as if it were whole.

RUSTSEC-2026-0258 turned the supply-chain gate red the same way: h2 queues empty DATA frames without
limit. It is reached as hyper -> axum / axum-server / reqwest, so it is in the daemon and the sync
transport rather than in a build-dependency. `deny.toml`'s rule is that a vulnerability in something
that ships gets no ignore, so the version moved instead - 0.4.18, past the 0.4.16 that patched it.

## The supply chain, including three majors

`ed25519-dalek` 3, `toml` 1.1, `getrandom` 0.4, `oxc` 0.143, `redb` 4.2, `rmcp` 3.1.4, and five
GitHub Action majors.

Two of the majors did not compile as offered. `getrandom` dropped the free function named after the
crate in 0.3 - it is `fill` now - and both call sites here are ones that must not silently degrade:
the MCP bearer token, and the ed25519 secret behind this node's federation identity. `toml` 1.0
changed `str::parse::<toml::Value>()` from "parse this document" to "parse this value expression",
which broke all three of `manifest_consistency.rs`'s tests: `[workspace]` read as an array literal
and everything after it as trailing content. `toml::Table` is the document type. That one is worth
naming because those three tests are what hold the version equal across the eight places it lives,
and with the parse broken they would have failed loudly while reporting nothing about drift.

`ed25519-dalek` 3 was checked against the federation rather than against the compiler, since a
signature made by a v0.3.0 node has to keep verifying on a node that upgrades and the reverse.
Building both versions into one binary: public keys identical, signature bytes identical, and both
verification directions hold. Nothing on the wire moved.
