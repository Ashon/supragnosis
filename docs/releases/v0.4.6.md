Changes since v0.4.5.

**Upgrade a hub that admits principals; nothing else needs doing.** On such a hub, a principal
could learn whether a named entity, or a sentence it guessed, was recorded in a workspace it was
never granted. Only a node with `[[server.principals]]` serves the surface this concerns - a node
without principals, and every local daemon, never did. The store, the sync protocol and every
client configuration are unchanged.

## An id outside the grants reads as an unknown one

The agent surface v0.4.5 added lets a hub's principals read and write the workspaces they are
granted. Asked for something by id, it answered an id in a workspace the principal was not granted
with "not in a workspace granted to alice", and an id that does not exist with "not found". Both
answers were true. But the ids are not secrets:
- an entity id is the hash of a workspace and a name;
- an observation id is the hash of a workspace and a content.

A principal who guessed a workspace name and an entity name, or a short sentence, could compute
the id, ask, and tell from the answer whether it was recorded there.
([docs/remote-viewer.md](https://github.com/Ashon/supragnosis/blob/main/docs/remote-viewer.md)
Section 3.4)

- **`get_entity`, `traverse`'s start and the observation resource** now give one answer for both
  cases: "no entity with that id in the workspaces you may read". That is true in both, does not call
  the entity absent, and does not say where else it might be.
- **A `claim_promotion` or `claim_demotion`** checked its target observations against the whole log,
  so its refusal for an absent target confirmed a present one elsewhere. On the agent surface it
  now names only observations in its own workspace, with one refusal for "absent" and "elsewhere".
- **A granted workspace the hub may not serve** still says why - which node has not consented -
  because the principal holds that grant.

Writing the design for the next step found it: browsing a remote server from the desktop app has
to answer the same question for every id the viewer reads.

## Also

- [docs/remote-viewer.md](https://github.com/Ashon/supragnosis/blob/main/docs/remote-viewer.md)
  specifies that next step. The hub would serve its viewer, read-only, to the principals it already
  admits, and the desktop app would show a remote server's knowledge instead of a notice that it
  cannot.
- The desktop app builds with tauri 2.12.1, and the server with http 1.5.0.
