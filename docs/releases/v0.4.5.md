Changes since v0.4.4.

**Nothing to do on upgrade; one thing worth doing.** An AI app connected the old way - `claude mcp
add ... --header "Authorization: Bearer $(cat ~/.supragnosis/mcp.token)"` - holds a copy of the
daemon's token in its own settings. `supragnosis connect claude-code --replace` (or a click in the
tray's AI Apps menu) switches it to the bridge and the copy goes with the old entry. The store and
the local MCP surface are unchanged, and the sync protocol gains only an optional header that an
older hub ignores; a hub gains a door only when its operator admits someone through it.

## Connecting an AI app no longer takes a terminal

Connecting a client meant typing a command that spliced the bearer token into the client's own
settings, and it did not reach Claude Desktop at all: its config takes local servers over stdio
only, and its Connectors UI is OAuth-only. The stdio server supragnosis shipped opened the store
itself, so it could not run beside the daemon either.
([docs/client-connect.md](https://github.com/Ashon/supragnosis/blob/main/docs/client-connect.md))

- **`supragnosis bridge`** is the stdio server an app launches now. It relays to the daemon,
  reads the token from its 0600 file on every request, opens no store and starts no daemon. A
  daemon restart is invisible to the app: the bridge replays the app's own handshake when the
  daemon answers 404 for the session it lost.
- **`supragnosis connect <app>`** registers the bridge with Claude Desktop, Claude Code, Cursor, VS
  Code, Codex or Gemini - through the app's own CLI where it has one, and by a one-member edit of
  its config file where it does not, backed up first and refused if the file does not parse. With
  no app it lists them and how each is connected.
- **The tray's AI Apps menu** does the same with a click, and says what to do next ("quit Claude
  and open it again").

## One client setup, any supragnosis server

A machine's AI apps can now use a supragnosis server on another machine, and the server decides
who may read and write what.
([docs/remote-server.md](https://github.com/Ashon/supragnosis/blob/main/docs/remote-server.md))

- **Server profiles.** `supragnosis server add <name> <url>` reads a credential from stdin into a
  0600 file; `server use <name>` points every AI app here at that server - their configuration stays
  `supragnosis bridge` - and `server use local` points them back. Remote URLs are HTTPS (plain HTTP
  to loopback only), and nothing turns certificate verification off. The tray gains a Server menu.
- **Principals.** On a hub, `supragnosis principal add alice --read docs --write team` admits a
  person or an agent to MCP at `/mcp` on the existing sync listener. The credential is shown once
  and stored as a hash; adding and revoking take effect without a restart. Every tool has a remote
  policy: reads and `observe`/`propose` within the grants; verdicts, type definitions and sync are
  refused until principals can sign their own acts. A remote write is recorded as the principal,
  whatever the client claimed.
- **Consent.** A spoke's shared knowledge reaches the hub's principals only if the spoke lists the
  workspace in `[sync] serve_workspaces`. It says so in a header on every sync round, which an older
  hub ignores; without it, the hub refuses and names the spoke rather than showing a partial view.

Hub operators: the bind rule now reads "TLS and someone admitted - a node or a principal". A hub
with no principals answers every `/mcp` request with 401.

## Also

- `supragnosis status` names the server this machine's AI apps use, and prints how to connect an app
  instead of a command carrying the token.
- README, the landing page and both installers show `supragnosis connect` rather than the
  token-carrying command or the store-opening stdio line.
