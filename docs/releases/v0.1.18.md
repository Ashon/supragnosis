Changes since v0.1.17.

Two halves. The first is cost: every fold on the read path is a pure function of the same rows and
each was fetching them for itself, so `graph` walked the observation log four times and `curation`
sixteen - `curation` being what the viewer's review tab polls every 2.5 seconds. A read walks it once
now. The merge band was worse in kind rather than degree: handed every entity of the workspace with
vectors included, it then asked the store for each one's nearest neighbours, which is N queries to
rank data already in hand.

The second half comes from a design-principle review, and three of the things it found have the same
shape - a guarantee that was written down, believed, and true only by accident. The one that mattered
had been quietly withholding 23 of the 141 observation rows in the author's own store from every fold
that reads them.

No id-formula or store-schema change, so no migration is needed, and the MCP tool surface is
unchanged. Upgrade is the usual `brew upgrade`, then `brew services restart supragnosis-server`.

**Three behavior changes worth knowing before you upgrade.** Observations that previously failed to
parse now participate in the folds; on the store this was measured against that meant the log browser
went from 118 entries to 136 and nothing else moved - graph, attestation counts, the 48 proposals and
the 65 type definitions all came back byte-identical - but a recovered row is a row that counts, so a
store whose unreadable rows carried proposal events or type definitions will see those folds change,
which is the point rather than a side effect. If you have ever run `migrate`, duplicate proposals
disappear on upgrade with no action needed: they were a fold artifact, not stored state. And a
client-supplied `source_ref` under the reserved `surface:` prefix is now refused at the ingest doors.

## Highlights

### Rows written before provenance became a list are readable again

`Observation.provenance` became a **list** of attestations when the re-arrival merge norm landed
(Principle 3): a second arrival at the same content address unions attestations instead of
overwriting. Rows written before that hold a single bare object, `Vec<Provenance>` cannot parse one,
and the reconstruction failed for the whole row - which was then excluded from the enumeration as a
degrade. It was logged, and the log said "original preserved", which was true and beside the point.

Keeping every historical encoding readable turns out to be a Principle 3 obligation rather than a
courtesy. The log is append-only, so a row can never be rewritten away; a row that stops parsing is
destroyed in effect, which is precisely the outcome that principle exists to forbid. Storage decoding
is where "nothing is destroyed" quietly stopped holding.

`migrate` could not have covered it, and not by oversight: migration walks `all_observations`, the
very enumeration an unreadable row falls out of, so the rows needing repair were exactly the ones it
could not see. The repair is therefore a permanent read shim, not a migration. The write path still
emits only the current encoding and the sync wire decoder is untouched, so the legacy shape can arrive
only from a node's own past.

The blast radius is narrower than it first looks, and worth stating precisely. Keyword and semantic
search read the observation table's columns directly and never reconstruct, so these rows were always
recallable. What was broken is everything downstream of reconstruction: the folds, the log browser,
`supragnosis://observation/{id}` dereference - so a search could return a hit whose provenance could
not be inspected, which is the one thing Principles 2 and 14 jointly promise - and `add_observation`'s
merge baseline, which propagates a read failure by design and therefore refused to absorb any
re-observation of that content at all.

### A read walks the observation log once

`ReadCtx` is a per-call snapshot of the rows, threaded through the folds. It is not a cache with an
invalidation problem: it is scoped to one call and never stored on the engine, so there is nothing to
invalidate. It carries the workspace scope beside the rows and reads through on a mismatch, because
answering a `Some("a")` read from rows loaded for `None` is not slower, it is wrong.

It also carries the log epoch it loaded at, and the engine bumps that epoch on every append, so a
context that outlives a write stops reusing rather than serving rows from before the write. Until
that guard existed the rule "do not read through a context after writing" held only because the calls
happened to be arranged that way - a statement about today's arrangement, not the next one.

### The merge band ranks in memory, and says one thing on both adapters

With an embedder configured the band cost 13.79s at 300 observations, against a review tab that polls
every 2.5 seconds, so the tab could not keep up with itself. Ranking the vectors already in hand
reproduces what the store returned exactly - same workspace filter, same cosine, same order, same
top-K cut, 84 candidate pairs before and after on the twelve-entity fixture.

The side effect is agreement. InMemory ranked exhaustively while Cozo ran an HNSW approximation, so
the same log could suggest different merges depending on which adapter was underneath. Computing it in
the engine closes that divergence before it was reachable, rather than after.

### Determinism that held by accident now holds by rule

An accepted `entity_merge` can fold two relations onto one `(from, kind, to)`, and `graph` resolved the
collision with "keep the first" over whatever order the adapter enumerated. The edge list was sorted -
by `(from, kind, to)`, the dedup key, which is exactly the sort that cannot disambiguate which
duplicate survived. On Cozo the answer was stable because RocksDB enumerates by primary key, which is
the relation id; on InMemory the same log and the same query returned a different edge description 18
times out of 40. Relations are now ordered by the stable key before anything picks among them.
Choosing among duplicates on merit would be relation belief resolution, which is deferred with
negation semantics; pinning the tie is not.

`migrate` had the mirror-image problem. It re-creates a pre-formula row under the current content
address and, the log being append-only, leaves the original in place - so one act appeared twice in
every fold. Content-address dedup normally prevents that; a re-keying is the one case where a single
content deliberately wears two ids, so the rule now gets applied by hand at the door every fold reads.
Measured on a two-row log: four rows after migration, the proposal list at two, an entity's supporting
attestations at two. The proposal was the sharp end, because a proposal's id is its opening
observation's id, so the copy was a second proposal no verdict could ever reference and it stayed open
forever.

## Fixes

- **A blocked gate merge grants nothing.** `fold_proposals` answers "did this merge commit", and
  `merge_forwarding` already refused to forward for a blocked one - `gate_grants` did not ask. Reachable
  through partial sync: a `claim_promotion` targeting one present and one absent observation, plus a
  replicated merge verdict, read blocked on every proposal surface while the present target's effective
  tier had already risen, to `HumanConfirmed` when the verdict carried the console marker. The state
  fold and the effect folds now give one answer.
- **The `surface:` marker namespace is reserved at the ingest doors.** The verdict-surface markers ride
  `source_ref`, and the ceiling fold trusts a log-borne marker to be engine-stamped. That trust rested
  on an inventory argument that was true and one refactor from false, since nothing refused the
  namespace itself. `observe`, `define_type` and `propose` now refuse a client-supplied `source_ref`
  under the prefix. Sync apply stays deliberately unguarded - a replicated verdict legitimately carries
  its marker, which is how the ceiling converges.
- **The viewer settles instead of cutting.** Damping and integration are not gated on the sim being
  active, so nodes coast after the last force, and testing alpha killed the render loop at the start of
  the coast and froze the layout mid-glide. The loop now tests the largest distance any node actually
  moved, in screen pixels so the threshold means the same thing at any zoom.
- **A settled graph stops redrawing.** `draw()` re-scheduled itself and re-rendered an identical image
  sixty times a second. A viewer left open on a settled graph is not an edge case, it is what the thing
  does while you work.

## Under the hood

- **The ledger and the coverage registry stopped answering differently.** Section 14 records what is
  owed and the registry mechanizes it, so a milestone that differs between them means one of the two is
  lying. Four had drifted - the M3b roadmap headline, the P11 induction milestone, the bitemporal
  milestone, and P21's narrowness, which sat under "currently satisfied" while the registry filed it as
  unguarded on the grounds that a tool count is not a predicate. The registry was right. Four debts that
  existed in the ledger and nowhere in the registry now have clauses: relation multi-attestation,
  `reproject` taking no write guard, the replicated console marker, and the informative checks.

- **A test claimed ground it did not cover.** `read_surfaces_do_not_depend_on_enumeration_order`
  reversed only `all_observations`, while the duplicate-edge defect rides `all_relations`, and its
  fixture had no merge so no duplicate edge could form. It reverses all three enumerations now. In the
  same vein, `p16_partitioned_and_duplicated_delivery_converges` compared the two nodes' graphs by shape
  - node ids and edge triples - which says nothing about the belief values, contested flags, effective
  tiers, aliases or edge metadata those carry. It compares them serialized whole and still passes,
  which closes the batch-partition sliver the ledger recorded. Comparison depth is not a detail: shape
  equality is exactly what let an order-dependent pick sit in `graph` with the suite green.

- **Enforcement is a mandate, not a status report.** Several Enforcement clauses in the normative
  document describe mechanisms that do not exist yet - quarantine, the self-approval check, the
  non-delegable recall verdict, the extraction port - and read as current behavior. The preamble now
  says which two places answer "is it built" and are tested against each other. Two clauses had gone
  further and asserted a fact: that a `query` Datalog passthrough exists under a permission guard. It
  has never been built, which is the stricter state, so the norm was describing a hole the code does not
  have.

- **The viewer's state-changing GETs rest on a corrected argument.** Three places said a browser cannot
  reach the unix socket. The desktop shell is a webview that reaches it, proxying path and query
  verbatim, and the curation console needs those endpoints. What actually holds is that no third-party
  origin can reach the socket, so CSRF and rebinding have no origin to come from - and naming it
  correctly names what is left over, which is stored XSS in a page that renders synced,
  attacker-influenceable content. That is the load-bearing reason the escaping guard and its lint exist.
  A Content-Security-Policy header is recorded as still owed.
