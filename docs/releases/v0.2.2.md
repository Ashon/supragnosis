Changes since v0.2.1.

**There is a container image now**, published to `ghcr.io` on every release, and a `server.json` that
registers this server with the [MCP Registry](https://modelcontextprotocol.io/registry/about). Nothing
about the daemon changed; this is the release where it becomes something you can find and install
without knowing it exists first.

## Running it as an MCP server from the image

```bash
docker run -i --rm -v supragnosis-state:/var/lib/supragnosis/.supragnosis \
  ghcr.io/ashon/supragnosis:0.2.2 serve
```

`serve` overrides the image's default command, which starts the HTTP daemon a federation hub wants.
`linux/amd64` and `linux/arm64`.

**The volume is not optional, and it matters more here than anywhere else.** An MCP client launches
this per session. The node key is written once and the node identity derives from it permanently, so
a session without the volume is not a restarted node - it is a new one with an empty log, which
looks like the tool not working rather than like a missing flag. `server.json` marks it required and
carries that reason in the argument's own description, where a client can show it.

Verified rather than assumed: an `observe` in one container is found by a `search_knowledge` in the
next, under the same node id.

## What the registry entry cost, and what it did not

The registry does not accept crates.io. The supported package types are npm, PyPI, NuGet, OCI and
MCPB - a launch review had assumed a crates.io publish was the prerequisite for registering, and it
is not one; it is not even an option. The container image built for hub deployment in v0.2.1 turned
out to be the whole of the answer.

Ownership of an OCI package is proved by an `io.modelcontextprotocol.server.name` label in the image
that must equal the `name` in `server.json` exactly. Two files that have to agree is a thing that
drifts, so the release workflow asserts it - the label, the version, and the image tag - and fails
rather than publishing a registry entry that points at an image nobody pushed.

The version now lives in three places: `Cargo.toml`, `app/Cargo.toml`, and `server.json`. That check
is what makes a missed bump a red build.

## Also

- **A supply-chain gate.** `cargo-deny` runs over both workspaces on one config: advisories,
  licences, bans, sources. SECURITY.md states a threat model in detail, and a project that does that
  while checking nothing about what its dependencies carry is asymmetric. The licence allow list was
  measured from the tree rather than guessed, and each entry that needed a reason has one - MPL-2.0
  arrives only through the CSS minifier, whose output ships and whose code does not.

  Unmaintained advisories are scoped to what this project chose. A crate named in a manifest here is
  a decision someone can revisit; one three levels down is upstream's schedule. Without that scoping
  the desktop shell fails on eighteen, every one of them Tauri's GTK3 Linux backend, which the macOS
  bundle never compiles.
- **Dependabot**, covering both workspaces. The shell's lockfile is invisible from the root, which is
  the same separation that keeps a webview advisory from reading as an advisory against the daemon.
- **crates.io publication is possible again.** Internal dependencies were declared path-only and
  cargo refuses to publish a crate whose dependencies carry no version requirement. Each now carries
  `version` beside `path`. Nothing is published; the reason it could not be is gone.
- **CODE_OF_CONDUCT.md**, and a **CHANGELOG.md** that indexes the release notes rather than
  duplicating them.
- **The release pipeline reads in English.** `release.yml` carried thirty-two lines of Korean and
  `.gitignore` three - the files a contributor opens to understand how a release is cut. Translated
  rather than dropped; the reasoning in them is why the pipeline is shaped the way it is.
- **A first minute in the README**, ending on provenance, with the viewer screenshot the landing page
  was already using. The quick start used to stop at "ask your agent to remember something", which
  leaves a reader installed and with nothing to type.
- The landing page's version badge is stamped through an authenticated API call. An anonymous one
  from a runner shares a rate limit with every other runner on that address, which is how the v0.2.1
  deploy failed and left the page naming v0.2.0.
