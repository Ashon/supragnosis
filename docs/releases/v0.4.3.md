Changes since v0.4.2.

**On macOS, give the daemon one manager after upgrading.** `supragnosis service install` now
generates the login job that keeps the daemon running, the desktop app's tray has a Start at Login
switch over the same job, and the Homebrew formula no longer has a `service do` block. What to run
depends on how the daemon runs today, and `supragnosis status` now says which that is.

- **Started with `brew services start supragnosis-server`:** the job keeps running the old binary
  after `brew upgrade`. Turn on Start at Login in the app, or run
  `supragnosis service install --take-over`. Either retires the brew services job through
  `brew services stop` and starts the new binary under `com.supragnosis.daemon`.
- **A LaunchAgent you wrote, or copied from the old `deploy/launchd/` template:** it keeps working,
  and `supragnosis restart` loads the new binary. `supragnosis service install --take-over` replaces
  it with a generated one; yours moves to `~/.supragnosis/launchd/`, and its `EnvironmentVariables`
  carry over verbatim.
- **Only the desktop app:** nothing to do. The app still runs a daemon for its session; turn on
  Start at Login if MCP clients should reach it with the app closed.
- **`supragnosis start`:** unchanged. `service install --take-over` stops it and installs the job.

After every later upgrade, `supragnosis restart` loads the new binary, whichever single manager runs
it. The store, the MCP surface and the sync protocol are unchanged.

## Why: two owners of one store

The v0.4.2 note said `brew services restart supragnosis-server` is what makes an upgrade visible. On
a machine whose daemon ran under a hand-written LaunchAgent, that command created a second job
beside it. redb admits one writer, so the new job failed on the store lock, and KeepAlive retried it
until its error log reached 6,124 lines. Meanwhile the old daemon kept serving v0.4.0 from a v0.4.2
install, and nothing reported either fact: `supragnosis status` knew one launchd label and saw a
healthy daemon, and the failing job wrote to a log nobody reads. Four things could start the daemon
(a LaunchAgent, brew services, `supragnosis start`, the desktop app), and the commands that control
it knew two of them.

The rule now, specified first in
[docs/daemon-lifecycle.md](https://github.com/Ashon/supragnosis/blob/main/docs/daemon-lifecycle.md),
is one manager. Every label the product has ever installed is recognized: the canonical one,
Homebrew's in its current and older forms, the retired formula token's, the pre-0.1.2 label, and the
pidfile. A loaded job counts even with no process, because a KeepAlive job failing on start is the
one that matters. With one manager, `status`, `restart` and `stop` act on it. With two they refuse
and print the command that resolves it, because restarting one of two owners is how a crash loop
gets a second wind. `status` also reports the version the daemon is running next to the installed
one, and reports "unknown" when the daemon does not answer instead of assuming.

## `supragnosis service install`

The login job is generated rather than templated: the program and `serve`, RunAtLoad, KeepAlive,
logs in `~/.supragnosis/log/`, and a marker naming the version that wrote it. A Homebrew install
names the `opt` link, which Homebrew repoints on upgrade, not the versioned keg the binary resolves
to.

Install refuses to share. Another manager is named and left alone unless `--take-over` is given,
which retires it: a brew services job through `brew services stop`, because the plist is Homebrew's
and a bootout alone would load it again at the next login. A plist without the marker was written by
a person, so it is moved aside under a timestamp, never overwritten or deleted. Its environment is
carried forward, because `SUPRAGNOSIS_HOST`, `_WORKSPACE`, `_EMBED` and `_DATA_DIR` exist only as
environment variables, and the host is recorded in the provenance of every new observation.
Dropping them on take-over would quietly change who the daemon says it is.

One refusal holds even with `--take-over`: something answering that no manager accounts for. The
likeliest is the desktop app's own daemon, which has no pidfile and no launchd job. Installing
beside it would rebuild the crash loop above from the command meant to end it, so install says what
it is probably looking at and points at the app's switch, which stops its own daemon before calling
the CLI. The case was found while writing these notes, before any release carried the command.

## The tray says who runs the daemon

The tray gains Start at Login and a status line naming the manager (login item, brew services,
`supragnosis start`, or this app). The line also reports a conflict, and says outright when an
upgraded binary sits under an older running daemon. It is re-read every minute, because an upgrade
replaces the binary without telling anyone. Restart Daemon now reports a refusal instead of
re-attaching to the process it failed to replace. The app decides nothing itself: it calls the CLI
it already finds, so the rules live once, in the code that is tested. With a CLI too old to know
`service`, the switch is disabled and says to update `supragnosis-server`.

## Homebrew gets what the repository says

The tap's formula and casks are now rendered from `deploy/homebrew/` on every release. The release
job used to edit the tap's own copies, version and sha256 only, so a change to a template's
structure never reached `brew upgrade`. This release would have shipped the new binary under the
old formula, still offering `brew services start`. Rendering v0.4.2 into a clone of the tap
differed from it only in that service block, so nothing else had drifted.

The curl installer (`supragnosis.dev/install.sh`) now prints `supragnosis service install` on
macOS, instead of a foreground command line and a pointer to `deploy/README.md`.

## The inspector groups relations

Step 2 of [docs/inspector.md](https://github.com/Ashon/supragnosis/blob/main/docs/inspector.md).
The busiest node's incoming edges were fifteen rows reading `<- part_of`, one per neighbour, and the
panel showed six of them. Relations now group by direction and kind. The kind is printed once, in
mono because it is an identifier, and its members follow as chips because they are names. Past six,
the chips fold behind a `+N` that expands in place. The same node shows all nineteen relations in
about eight lines. A superseded edge stays listed, dashed, never dropped. The panel keeps its 36vh
default so the graph stays visible, and a control beside close trades it for 72vh, remembered
across nodes.

## Also

- Building from source needs Rust 1.96: oxc 0.152, which minifies the viewer in release builds,
  declares it. The CI job that checks the floor builds with exactly the declared version.
- rmcp 3.5 (`ServerInfo` is renamed `ServerConfig`, with no wire change), redb 4.3, axum-server
  0.8, tauri 2.12.
- fastembed 7, for source builds with `--features fastembed`. Its embed call now takes `&mut self`,
  so the shared model sits behind a mutex, and concurrent embeds on one daemon queue. The same model
  snapshot embeds identically under 4.9.1 and 7.1.0 (cosine 1.0 on eight sentences including
  Hangul), so stored vectors stay comparable. CI now builds the feature: the bump to 7.1 was green
  there and did not compile.
- The Rust gate runs weekly on main as well. It can go red with no change to the tree (a yanked
  crate, a new advisory, a new stable lint), and all three happened between v0.4.1 and v0.4.2. The
  sync TLS listener is now tested end to end, accepting HTTPS and refusing plaintext.
